# Основная память агента (`core.md`)

> Заполняется на З1, дополняется каждое занятие. Здесь хранятся факты, правила и примеры, которые агент должен учитывать. После правки агент перечитывает файл, а человек проверяет результат.

## Факты о бизнесе

- Инвестиционный фонд, аналитика по рынку США, фонд предлагает идеи, которые дальше покрывает и обновляет.
- Аналитик ведёт несколько компаний: знает бизнес, строит модель оценки, регулярно обновляет её по новостям, отчётам и событиям сектора.
- Текущее покрытие владельца — урановые компании и майнинговые компании (тикеры пока не названы).
- При выходе отчётности: сбор данных + обновление модели → оценка изменений → комментарий о том, как компания отчиталась относительно внутренних прогнозов и ожиданий рынка. Пример готового комментария — `Nebius 2Q26 Earnings Summary` в `OME Examples/Nebius (NBIS US)`.
- Проблема: не успевает качественно покрывать все компании из списка; сбор данных и обновление модели при выходе отчёта занимает много времени; бывали случаи, что компания забывалась и вспоминалась только на следующий день.
- Первый этап автоматизации — именно сбор данных, с акцентом на стабильность работы агента (не на скорость и не на готовый комментарий).
- Первая функция под автоматизацию рассматривается на масштабе ОДНОЙ компании; предполагаемое узкое место — сам владелец (аналитик) из-за ограниченной пропускной способности, а не спрос/данные/деньги. Требует подтверждения на З2 по `process-map.md`.
- С 2026-08-25 функция расширена решением владельца: помимо сбора/сверки данных агент теперь готовит интерпретацию результатов и реакции рынка (см. «Правила» ниже и `agent/contract.md` v1.1). Первый пример нового формата — `Walmart_отчетность_реакция_рынка.md` (Q2 FY27, разбор 2026-08-20/25).

## Правила (что можно и нельзя)

- Если ключевого источника нет на момент проверки (например, транскрипт звонка ещё не опубликован на investing.com или звонок ещё идёт) — агент прямо пишет «не нашёл X», не додумывает и не молчит, и сам ставит себе задачу перепроверить через ~1 час.
- Разрешённые источники для сбора данных (первый прогон): investing.com (транскрипт), сайт IR компании (пресс-релиз, презентация), Yahoo Finance как запасной источник транскрипта. Bloomberg API и общая рыночная реакция — вне рамок первого прогона.
- В итоговой заметке/выгрузке всегда явно указывается, на основе каких источников она собрана и что именно не найдено или вызывает сомнение — провенанс обязателен для каждой цифры.
- Приоритетный показатель — не сам факт метрики, а ИЗМЕНЕНИЕ гайденса компании относительно предыдущего гайденса (не только факт против консенсуса/старого гайденса разово, а именно динамика ожиданий).
- Обязательные метрики для комментария: Revenue, EBITDA, EPS, Margin, Capex — текущая динамика + при наличии гайденс и его изменение.
- Расстановка акцентов не произвольна: для каждого типа компании рынок обычно смотрит на 1–2 ключевые метрики. Общий принцип — отслеживать нефинансовые опережающие метрики юнит-экономики, на их основе прогнозировать финансовые (выручку, маржу); отдельно отслеживать вторую производную (темп роста самого роста) как предиктор будущих денежных потоков.
  - Гиперскейлеры: изменение гайденса по capex на будущий год + темпы роста облачного сегмента.
  - Направления, которые рынок уже полностью заложил в цену (например, Xbox для MSFT) — не подсвечивать отдельно, упомянуть только при декомпозиции.
  - Neo-cloud (например, Nebius): бэклог/объём законтрактованных сделок + темп роста выручки (и его вторая производная).
  - AI-лаборатории: ARR, число пользователей, средний чек.
  - Ритейл (например, Walmart): сопоставимые продажи (comp sales) по сегментам, доля e-commerce в продажах и её вклад в рост (в б.п.), гайденс по темпу роста операционной прибыли квартал-к-кварталу — не только сам факт бита. На Walmart Q2 FY27 именно резкое замедление гайденса по марже (с +23,3% факта до +2,0–4,0% прогноза на Q3) объяснило обвал акций на 9% при формальном бите по выручке и EPS — прямое подтверждение правила про «вторую производную» выше: рынок реагирует не на факт бита, а на изменение ТЕМПА роста показателя.
  - Ядерный топливный цикл/обогащение урана (например, Centrus Energy, LEU): объём и горизонт законтрактованного бэклога (годы вперёд), правительственные контракты (например, DOE), offtake-соглашения с разработчиками реакторов (SMR) — не квартальный GAAP EPS, он у таких компаний по природе волатилен (учёт цен SWU, структура затрат) и не был главным ориентиром ни для рынка, ни для менеджмента. Подтверждено на LEU 2К26: акция выросла на 7,5% при падении GAAP-прибыли почти вдвое — рынок реагировал на рост бэклога до $4,5 млрд, контракт с DOE на $900 млн и новые HALEU-сделки (Oklo, X-Energy), не на факт отчёта.
  - Список не исчерпывающий — уточняется по мере разбора новых типов компаний.
- Приоритет по типам исходных документов при расхождении цифр: официальный PDF пресс-релиза/financial results > shareholder letter компании > транскрипт звонка > агрегаторы новостей. Shareholder letter НЕ содержит EPS (ни GAAP, ни Adjusted) — по крайней мере для Nebius, проверено на 5 письмах подряд; для EPS нужен отдельный "Financial results" PDF или 6-K.
- SEC EDGAR (sec.gov) блокирует автоматические запросы агента (403 Forbidden) — не полагаться на прямые 6-K как на источник без отдельной проверки доступа.
- Технически: PDF-документы нужно сначала скачать (fetch), затем читать как PDF-файл напрямую — попытка распарсить PDF как текст веб-страницы не работает.
- **Интерпретация (с 2026-08-25) — новый контур функции.** Помимо цифр, агент теперь готовит интерпретацию результатов и реакции рынка, обязательно основанную на найденных открытых источниках (новости, обзоры, инвестинг.com summary/консенсус-блок, комментарии аналитиков) — не домысливает сверх того, что подтверждено источниками. Приоритет источников для самих ЦИФР не меняется (см. пункт выше); открытые новости — отдельный, дополнительный контур сбора именно для интерпретации, не замена приоритета для фактов. Документ не считается завершённым без списка источников (ссылок) в конце — это обязательный элемент формата, не опция. Формат-ориентир: `Walmart_отчетность_реакция_рынка.md` (структура: цифры → реакция рынка → причины расхождения, какие метрики двинули цену → источники) и лекала стиля/глубины в `examples/report-style-templates.md`.
- **«Темы момента»** — краткосрочные, специфичные именно для текущего отчёта факторы в фокусе рынка, отдельно от постоянных метрик playbook выше (пример: разрешения на строительство ЦОД для Nebius, которые сейчас часто отклоняют по политическим причинам). Фиксировать отдельной строкой по мере обнаружения при разборе каждой отчётности — они не остаются в плейбуке навсегда, в отличие от метрик выше.
- **Хранение по компании (открытый вопрос, решение не принято).** Идеальный формат — отдельный, постоянно дополняемый .md-файл на компанию (не разовый прогон), растущий по мере покрытия отчётностей и новостей. Владелец хранит такие заметки на Диске X, который не всегда подключён — прогресс всегда должен сохраняться минимум локально; механизм дозаписи на Диск X при подключении (Python-скрипт или Планировщик задач Windows) обсуждается отдельно с владельцем, пока не выбран.
> Пример. «Цены ниже X не предлагать. Тон в письмах — на „ты“. Всегда прикладывать ссылку на бриф.»

## Структура папки компании — 6 папок (с 2026-08-26, по эталону фирмы — `LSI (LYTS)`)

Владелец показал реальный эталонный пример структуры (папка `LSI (LYTS)`, используется в фирме шире, не только в его собственном покрытии) и распорядился наложить эту же схему на архив агента. 5 папок — статичные названия на английском (как в эталоне, не переводим), дробится по годам только `Reporting`; 6-я папка — добавлена владельцем специально под то, что не укладывается в логику остальных пяти (агентские служебные/кэш-файлы — таких документов в эталоне нет, потому что там нет агента).

| Папка | Критерий (кто автор / что это) | Дробится по годам? |
|---|---|---|

| `Press\` | Третья сторона (СМИ) описывает ФАКТ/событие о компании, без инвестиционного тезиса — было `Новости\` | нет |
| `Model\` | Финансовая модель/DCF — рабочий файл, создаёт и правит только владелец; агент читает (Приоритет №1 для интерпретации), не редактирует | нет |

Ключевое разграничение: `Reporting` — сырьё (документ пришёл от компании как есть), `Analysis` — интерпретация этого сырья агентом/владельцем, `Agent's suggestions` — не аналитический контент для читателя вообще, а инфраструктура самого агента (кэш институциональной памяти, канал обратной связи). Один и тот же квартал даёт файлы в `Reporting` и `Analysis` одновременно, но никогда не смешивает их в одной папке.

Миграция уже собранных архивов (NBIS US и др.) на новую схему — отдельная задача, не выполняется автоматически этой правкой памяти; владелец подтвердил (2026-08-26): новую схему применять начиная со следующих прогонов, не мигрировать задним числом.

**Глубина архива `Reporting\<год>\` — правило с 2026-08-26.** Если для компании отсутствуют документы (call/release/presentation) за 4 предшествующих квартала — их нужно добрать при ближайшем прогоне, но только технически (скачать и сохранить), без сверки/интерпретации по ним — это докомплектация архива, не 4 отдельных полных прогона. Если компания публична меньше 4 кварталов — добирать только реально существовавшие. Пробел по историческому документу не эскалируется как для текущего квартала — просто отмечается, что не найден. Подробности процедуры — `agent/sop.md`, шаг 0b.
- **Диск X не всегда подключён** (см. также ниже, «Автоматизация и хранение прогресса»). Если недоступен на момент прогона — сохранять как минимум локально (Desktop) и не терять результат; синхронизация на X — см. `automation/`.

- `X:\Research\VS\Coverage\` — НЕ список тикеров с датами отчётности, а материалы по секторам целиком (`Mining`, `OIL`, `REE`, `Uranium`) — модели секторов, данные агрегаторов, записки банков. Список конкретных тикеров в покрытии с датами отчётности пока не формализован (владелец подтвердил 2026-08-25: работаем по одной компании за раз, без реестра).

## Правка инструмента: `html_to_text.py` уничтожал табы (найдено 2026-08-25)

Строка нормализации пробелов (`re.sub(r'[ \t]+', ' ', text)`) схлопывала не только лишние пробелы, но и намеренно расставленные табы-разделители колонок таблиц — из-за этого таблицы в пресс-релизах никогда не конвертировались в HTML-таблицы, хотя выглядело, что часть конвертируется (те таблицы на деле были из транскрипта, отрисованного через Playwright, а не из пресс-релиза через этот скрипт — легко перепутать при проверке). Исправлено: схлопывать теперь только `[ ]{2,}` (пробелы), таб не трогать. Второй попутный баг: источники часто вставляют пустые `&nbsp;`-ячейки только для отступа — при разбивке по табам это давало кучу пустых колонок; теперь пустые (после очистки `\xa0`) ячейки построчно дропаются. Урок: при проверке «заработало ли» — проверять, что результат пришёл именно из ожидаемого источника/шага, а не просто что артефакт (таблица) где-то в файле присутствует.

## Профиль компании — `<Тикер>_Description.md` (с 2026-08-25)

Чтобы не обращаться к базе `Research` (dsp-w-mssql-1) при КАЖДОМ прогоне, внутренняя аналитика по компании кэшируется в отдельный файл — живёт в папке `Agent's suggestions\` (см. «Структура папки компании» выше): `X:\Research\VS\<Тикер> US\Agent's suggestions\<Тикер>_Description.md`.

**Логика (по умолчанию, без явного запроса владельца):**
1. Файл `<Тикер>_Description.md` есть в `Agent's suggestions\`?
   - **Нет** → запрос в базу `Research` (история заметок по компании — кто из аналитиков писал, когда, какой был тезис) + чтение уже имеющихся локальных файлов (`Reporting\<год>\`, `Buy Side\`, `Press\`, `Model\`) → собрать файл впервые.
   - **Да** → смотреть дату «Обновлено» внутри файла.
     - **≤ 1 месяц назад** → использовать файл как есть, к базе НЕ обращаться.
     - **> 1 месяца назад** → повторный запрос к базе (обновить историю заметок), обновить файл, обновить дату «Обновлено».
2. Файл дальше дополняется/редактируется по мере появления новых материалов (например, файлов по внешней аналитике) — не только при устаревании по времени.

**Структура файла** (черновик, уточняется по практике):
```
# <Компания> (<Тикер>) — профиль компании
Обновлено: <дата>
Собран из: ResearchNotes (N заметок, авторы: ...) + локальные файлы (список)

## История заметок по компании (внутренняя аналитика)
| Дата | Автор | Заголовок | Тезис/рекомендация (кратко) |

## Эволюция тезиса
## На какие метрики смотрит аналитик по этой компании
## Темы момента (краткосрочные факторы в фокусе)
## Локальные материалы уже в архиве
```

Первый пример собран (2026-08-25) — `X:\Research\VS\NBIS US\NBIS_Description.md` (до миграции на новую 6-папочную схему лежал в корне папки тикера, не в `Agent's suggestions\` — путь нужно будет поправить при переносе), на основе 5 заметок аналитика Кирилла **Панарина** (UserID=3, не «Понарин» — уточнено при поиске в базе) по Nebius из базы `Research`, 2025-05-21 – 2026-07-08 из 13 найденных. Вскрыт открытый вопрос: прямой join `Companies.ObjectID` → `ResearchNotes.ObjectID` не сработал для другой компании (Cameco, ObjectID=910, входит в `CoverageList`, но вернул 0 заметок) — рабочий метод поиска пока LIKE-поиск по `Title`/`Tags`/`Text`, не ObjectID-join; надёжный общий механизм связки заметка↔компания для будущих тикеров ещё не найден.

## Обратная связь по черновикам агента — `<Тикер>_Feedback.md` (с 2026-08-26)

Отдельный от `<Тикер>_Description.md` механизм — не про историю тезиса компании, а про то, насколько черновик САМОГО АГЕНТА (Публикация/Как собран) разошёлся с тем, что владелец реально опубликовал или хотел бы поправить. Живёт там же — `X:\Research\VS\<Тикер> US\Agent's suggestions\<Тикер>_Feedback.md`. Полностью опциональный, необязательный шаг: используется только если владелец сам решил что-то приложить.

**Формат — один ПЕРЕЗАПИСЫВАЕМЫЙ файл, не растущий журнал** (в отличие от `Description.md` и от журнала «ошибка → правка» ниже). Решение владельца (2026-08-26): один предсказуемый файл проще для быстрой идентификации и sanity-check, чем лог из many записей — вся история правок и так не теряется, потому что оседает в постоянных местах (журнал ниже, `examples/report-style-templates.md`), а не в самом файле обратной связи.

**Что там может лежать (по желанию, необязательно оба сразу):**
- Финальный текст реально опубликованной заметки, если он заметно разошёлся с черновиком агента.
- Короткий комментарий без полного текста — просто что не понравилось / с чем не согласен.

**Логика проверки (шаг 0 SOP, вместе с проверкой `Description.md`):** агент читает файл, смотрит дату внутри него.
- Дата новее последней уже разобранной обратной связи (сверяется по датам в журнале «ошибка → правка» ниже) → разбирает: смысловая/фактическая правка → новая строка в журнале ниже; стилевая правка → `examples/report-style-templates.md` (или личный стилевой профиль по аналогии с `kanyuka-style`, если/когда он появится).
- Дата совпадает с уже разобранной — пропускает, ничего не переделывает.
Файл после разбора агент НЕ очищает и не перезаписывает сам — следующая перезапись новой обратной связью полностью на владельце.

## Методология Equity Research — новый контур (с 2026-08-25)

По системному промпту владельца добавлен второй, более строгий аналитический контур поверх уже существующего (сбор+сверка+короткая интерпретация). Не заменяет существующие правила источников для цифр — добавляет отдельную ось для интерпретации.

**Иерархия для ИНТЕРПРЕТАЦИИ (не для самих цифр — приоритет цифр не меняется, см. выше):**
- **Приоритет №1, мастер-источник** — внутренняя аналитика владельца: всё, что уже лежит в `X:\Research\VS\<Тикер> US\` (модели, DCF, питчи, записки, «Мнения инвест домов», «Новости») — это отражает то, что владелец УЖЕ знает/думает про компанию. Перед интерпретацией — прочитать, что там есть, и явно сверять новый отчёт с этим внутренним видением (совпадает / расходится / внутренняя модель не учитывала X).
- **Приоритет №2, вспомогательный бенчмарк** — внешний консенсус (Bloomberg/Reuters через вторичные источники, sell-side) — используется, чтобы понять ОЖИДАНИЯ рынка и найти «слепые зоны» рынка относительно внутреннего видения, не как самостоятельный источник истины.

**Логика анализа за пределами «бит/промах»:**
1. **Декомпозиция сюрприза.** Если EPS «бит» — выяснить, за счёт чего: операционные драйверы (объём, маржа) — качественный бит; более низкая налоговая ставка / разовые неоперационные статьи / изменение принципов амортизации — низкокачественный бит, в анализе явно понижается в весе, а не игнорируется молча.
2. **Вторая производная** (уже было в плейбуке ниже, теперь формализовано отдельно) — ускорение/замедление операционных метрик (не только фин. показателей) важнее самого факта совпадения с консенсусом. Замедление роста клиентской базы при устойчивой выручке — опережающий индикатор ухудшения, даже если квартал формально «в рынке».
3. **Пересмотр форвардных ожиданий.** Важнее реакции на факт прошедшего квартала — куда сдвинулись прогнозы аналитиков на 2 года вперёд (forward EPS/EBITDA) после отчёта.

**Плейбук по стадии/типу бизнеса — расширение существующего списка по секторам:**
- Зрелый капиталоёмкий бизнес: ROIC, CapEx/D&A, Cash Conversion Cycle, DSO, DOH (рост DOH при падении оборачиваемости запасов — риск затоваривания/списания).
- Быстрорастущий SaaS/платформа: органический рост выручки (без валютных/M&A эффектов), Net Retention Rate, LTV/CAC; капитализировать скрытые R&D-инвестиции для расчёта истинного ROIC (GAAP занижает его, списывая R&D в текущие расходы).
- Цикличный/сырьевой бизнес: не судить по пиковым/донным показателям цикла — смотреть объёмы производства, издержки на единицу, положение на кривой себестоимости отрасли; нормализовать маржу и рост к «середине цикла».

**Проверка качества прибыли (Earnings Quality Check) — новый обязательный блок для глубокого разбора:**
- Расхождение чистой прибыли и операционного денежного потока (CFO) — растущая прибыль при падающем CFO = красный флаг агрессивного признания выручки.
- Резкие колебания резервов (сомнительные долги, гарантии, обесценение запасов) — возможное сглаживание прибыли менеджментом.
- Необычный рост капитализируемых активов (PP&E/НМА) при стабильной марже на фоне спада в отрасли — риск неправомерной капитализации операционных издержек.

**Оценка стоимости (DCF/Multiples Impact) — новая, ограниченная часть контракта v1.2:**
Владелец решил (2026-08-25): агент теперь СЧИТАЕТ влияние выявленных за квартал факторов на допущения модели (терминальный рост, траектория ROIC к WACC, ставка дисконтирования) — но не выдаёт готовую целевую цену как инвестрекомендацию. В коротком публикуемом комментарии — это ОДИН обособленный абзац с чёткой пометкой начала/конца, специально для того, чтобы владелец мог его безшовно удалить или переписать перед реальной публикацией. В глубоком разборе (вкладка «Глубокий анализ») — этот блок разворачивается подробнее. См. `agent/contract.md` v1.2, `agent/escalation.md`.

## Формат «OME Report» — доработки после обратной связи (2026-08-25)

- **Транскрипт**: обрезка убирала мусор только В КОНЦЕ (после «This article was generated»), но не в НАЧАЛЕ — шапка сайта (меню, промо, виджет котировки) просачивалась в начало вкладки. Исправлено: ищем первый абзац длиннее ~120 символов (реальный лид статьи), всё до него — отрезаем. Заодно нашли, что реальный лид-абзац + «Key Takeaways» инвестинг.com — это ценная часть саммари источника, которую раньше срезали вместе с мусором (начинали с «Executive Commentary», а не с лида).
- **Пресс-релиз**: жирный текст (`<strong>`/`<b>` в исходном HTML) раньше терялся при конвертации в текст — теперь `html_to_text.py` сохраняет его как `**маркеры**`, а `build_report_html.py` рендерит их как `<strong>`.
- **Копирование таблиц**: кнопка «📋 Копировать в Excel» у каждой HTML-таблицы, копирует TSV (табами) через `document.execCommand('copy')` — совместимо с `file://`, в отличие от современного Clipboard API.
- **Комментарий — два раздела** внутри вкладки (переключатель-пилюля): «Публикация» (готовый текст в доме. стиле, см. `examples/report-style-templates.md`) и «Как собран» (рабочие заметки — расхождения, что не проверено). `build()` теперь принимает ОБА пути (`publication_path`, `commentary_path`) отдельно.

## Формат «OME Report» — второй раунд правок (2026-08-25)

- **Заголовки секций** (Key Takeaways, Company Performance, Financial Highlights, Risks and Challenges, Q&A и т.д.) теперь распознаются по известному списку (`KNOWN_HEADERS`) и рендерятся как `<h3>`, а не сливаются с обычным текстом.
- **Буллеты**: источник часто разделяет пункты списка ОДИНАРНЫМ переносом строки (не пустой строкой) — из-за этого весь список раньше слипался в один абзац/один `<li>`. Теперь после заголовка из `KNOWN_LIST_HEADERS` (Key Takeaways, Risks and Challenges, Financial Highlights) блок дробится построчно на реальные пункты `<li>`.
- **Таблицы**: добавлено объединение ячеек «$» + число в одну (было две колонки), подсветка строк «Total/Net loss/EBITDA» жирным, и вынос сплошного colspan-заголовка (короче остальных строк) в подпись-капшн над таблицей вместо кривой `<th>`-строки.
- **4-я вкладка «Презентация»** (опционально) — встраивает PDF инвесторской презентации КАК ЕСТЬ через `<iframe>` (плюс ссылка «открыть в новой вкладке») — не пересобирается в текст, показывается оригинал. Параметр `presentation_pdf` в `build()`, относительный путь от папки с итоговым HTML.

## Формат «OME Report» (с 2026-08-25)

По просьбе владельца — вместо (в дополнение к) разрозненных .md/.txt/.pdf файлов собирается единый HTML-файл на вкладках для удобного локального чтения: **Комментарий** (интерпретация) / **Пресс-релиз** / **Транскрипт**. Название формата — «**OME Report**», не публикуется никуда (не Artifact, не веб), только локальный файл, открывается двойным щелчком в браузере. Имя файла: `<Тикер> <квартал> - отчёт.html`, лежит в `Analysis\` (см. «Структура папки компании» выше): `X:\Research\VS\<Тикер> US\Analysis\<Тикер> <квартал> - отчёт.html`. Собирается скриптом `automation/build_report_html.py` (не писать HTML/конвертацию текста вручную заново). Акцентный цвет — `#1B2A6B` (тот же тёмно-синий, что уже используется в PPTX-материалах владельца — для визуальной согласованности). Первый пример — `X:\Research\VS\XE US\XE 2Q26 - отчёт.html`. Известное ограничение: если исходная HTML-таблица в релизе оформлена не через `<td>`, а неразрывными пробелами (`&nbsp;`) — такая таблица не конвертируется в HTML-таблицу и остаётся текстом; обычно это дублирующая "summary"-таблица, а не единственный источник цифр — не критично.

## Автоматизация и хранение прогресса (с 2026-08-25)

- Идеальный формат хранения по компании — растущий .md-файл, не разовый прогон (см. «Правила» выше). Реальное место — `X:\Research\VS\<Тикер> US\`, но диск не всегда подключён.
- Решение: локальный стейджинг + скрипт синхронизации на диск X при подключении, запускается через Планировщик задач Windows. Детали, скрипт и инструкция по настройке — `automation/README.md` и `automation/sync-to-diskX.ps1` в этом репозитории.
