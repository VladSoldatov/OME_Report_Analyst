# Основная память агента (`core.md`)

> Заполняется на З1, дополняется каждое занятие. Здесь хранятся факты, правила и примеры, которые агент должен учитывать. После правки агент перечитывает файл, а человек проверяет результат.

## Факты о бизнесе

- Инвестиционный фонд, аналитика по рынку США, фонд предлагает идеи, которые дальше покрывает и обновляет.
- Аналитик ведёт несколько компаний: знает бизнес, строит модель оценки, регулярно обновляет её по новостям, отчётам и событиям сектора.
- Текущее покрытие владельца — урановые компании и майнинговые компании (тикеры пока не названы).
- При выходе отчётности: сбор данных + обновление модели → оценка изменений → комментарий о том, как компания отчиталась относительно внутренних прогнозов и ожиданий рынка. Пример готового комментария — `Nebius 2Q26 Earnings Summary` в `OME Examples/Nebius (NBIS US)`.
- Проблема: не успевает качественно покрывать все компании из списка; сбор данных и обновление модели при выходе отчёта занимает много времени; бывали случаи, что компания забывалась и вспоминалась только на следующий день.
- Первый этап автоматизации — именно сбор данных, с акцентом на стабильность работы агента (не на скорость и не на готовый комментарий).
- Первая функция под автоматизацию рассматривается на масштабе ОДНОЙ компании; предполагаемое узкое место — сам владелец (аналитик) из-за ограниченной пропускной способности, а не спрос/данные/деньги. Требует подтверждения на З2 по `process-map.md`.
- С 2026-08-25 функция расширена решением владельца: помимо сбора/сверки данных агент теперь готовит интерпретацию результатов и реакции рынка (см. «Правила» ниже и `agent/contract.md` v1.1). Первый пример нового формата — `Walmart_отчетность_реакция_рынка.md` (Q2 FY27, разбор 2026-08-20/25).

## Правила (что можно и нельзя)

- Если ключевого источника нет на момент проверки (например, транскрипт звонка ещё не опубликован на investing.com или звонок ещё идёт) — агент прямо пишет «не нашёл X», не додумывает и не молчит, и сам ставит себе задачу перепроверить через ~1 час.
- Разрешённые источники для сбора данных (первый прогон): investing.com (транскрипт), сайт IR компании (пресс-релиз, презентация), Yahoo Finance как запасной источник транскрипта. Bloomberg API и общая рыночная реакция — вне рамок первого прогона.
- В итоговой заметке/выгрузке всегда явно указывается, на основе каких источников она собрана и что именно не найдено или вызывает сомнение — провенанс обязателен для каждой цифры.
- Приоритетный показатель — не сам факт метрики, а ИЗМЕНЕНИЕ гайденса компании относительно предыдущего гайденса (не только факт против консенсуса/старого гайденса разово, а именно динамика ожиданий).
- Обязательные метрики для комментария: Revenue, EBITDA, EPS, Margin, Capex — текущая динамика + при наличии гайденс и его изменение.
- Расстановка акцентов не произвольна: для каждого типа компании рынок обычно смотрит на 1–2 ключевые метрики. Общий принцип — отслеживать нефинансовые опережающие метрики юнит-экономики, на их основе прогнозировать финансовые (выручку, маржу); отдельно отслеживать вторую производную (темп роста самого роста) как предиктор будущих денежных потоков.
  - Гиперскейлеры: изменение гайденса по capex на будущий год + темпы роста облачного сегмента.
  - Направления, которые рынок уже полностью заложил в цену (например, Xbox для MSFT) — не подсвечивать отдельно, упомянуть только при декомпозиции.
  - Neo-cloud (например, Nebius): бэклог/объём законтрактованных сделок + темп роста выручки (и его вторая производная).
  - AI-лаборатории: ARR, число пользователей, средний чек.
  - Ритейл (например, Walmart): сопоставимые продажи (comp sales) по сегментам, доля e-commerce в продажах и её вклад в рост (в б.п.), гайденс по темпу роста операционной прибыли квартал-к-кварталу — не только сам факт бита. На Walmart Q2 FY27 именно резкое замедление гайденса по марже (с +23,3% факта до +2,0–4,0% прогноза на Q3) объяснило обвал акций на 9% при формальном бите по выручке и EPS — прямое подтверждение правила про «вторую производную» выше: рынок реагирует не на факт бита, а на изменение ТЕМПА роста показателя.
  - Ядерный топливный цикл/обогащение урана (например, Centrus Energy, LEU): объём и горизонт законтрактованного бэклога (годы вперёд), правительственные контракты (например, DOE), offtake-соглашения с разработчиками реакторов (SMR) — не квартальный GAAP EPS, он у таких компаний по природе волатилен (учёт цен SWU, структура затрат) и не был главным ориентиром ни для рынка, ни для менеджмента. Подтверждено на LEU 2К26: акция выросла на 7,5% при падении GAAP-прибыли почти вдвое — рынок реагировал на рост бэклога до $4,5 млрд, контракт с DOE на $900 млн и новые HALEU-сделки (Oklo, X-Energy), не на факт отчёта.
  - Список не исчерпывающий — уточняется по мере разбора новых типов компаний.
- Приоритет по типам исходных документов при расхождении цифр: официальный PDF пресс-релиза/financial results > shareholder letter компании > транскрипт звонка > агрегаторы новостей. Shareholder letter НЕ содержит EPS (ни GAAP, ни Adjusted) — по крайней мере для Nebius, проверено на 5 письмах подряд; для EPS нужен отдельный "Financial results" PDF или 6-K.
- SEC EDGAR (sec.gov) блокирует автоматические запросы агента (403 Forbidden) — не полагаться на прямые 6-K как на источник без отдельной проверки доступа.
- Технически: PDF-документы нужно сначала скачать (fetch), затем читать как PDF-файл напрямую — попытка распарсить PDF как текст веб-страницы не работает.
- **Интерпретация (с 2026-08-25) — новый контур функции.** Помимо цифр, агент теперь готовит интерпретацию результатов и реакции рынка, обязательно основанную на найденных открытых источниках (новости, обзоры, инвестинг.com summary/консенсус-блок, комментарии аналитиков) — не домысливает сверх того, что подтверждено источниками. Приоритет источников для самих ЦИФР не меняется (см. пункт выше); открытые новости — отдельный, дополнительный контур сбора именно для интерпретации, не замена приоритета для фактов. Документ не считается завершённым без списка источников (ссылок) в конце — это обязательный элемент формата, не опция. Формат-ориентир: `Walmart_отчетность_реакция_рынка.md` (структура: цифры → реакция рынка → причины расхождения, какие метрики двинули цену → источники) и лекала стиля/глубины в `examples/report-style-templates.md`.
- **«Темы момента»** — краткосрочные, специфичные именно для текущего отчёта факторы в фокусе рынка, отдельно от постоянных метрик playbook выше (пример: разрешения на строительство ЦОД для Nebius, которые сейчас часто отклоняют по политическим причинам). Фиксировать отдельной строкой по мере обнаружения при разборе каждой отчётности — они не остаются в плейбуке навсегда, в отличие от метрик выше.
- **Хранение по компании (открытый вопрос, решение не принято).** Идеальный формат — отдельный, постоянно дополняемый .md-файл на компанию (не разовый прогон), растущий по мере покрытия отчётностей и новостей. Владелец хранит такие заметки на Диске X, который не всегда подключён — прогресс всегда должен сохраняться минимум локально; механизм дозаписи на Диск X при подключении (Python-скрипт или Планировщик задач Windows) обсуждается отдельно с владельцем, пока не выбран.
> Пример. «Цены ниже X не предлагать. Тон в письмах — на „ты“. Всегда прикладывать ссылку на бриф.»

## Правка инструмента: `html_to_text.py` уничтожал табы (найдено 2026-08-25)

Строка нормализации пробелов (`re.sub(r'[ \t]+', ' ', text)`) схлопывала не только лишние пробелы, но и намеренно расставленные табы-разделители колонок таблиц — из-за этого таблицы в пресс-релизах никогда не конвертировались в HTML-таблицы, хотя выглядело, что часть конвертируется (те таблицы на деле были из транскрипта, отрисованного через Playwright, а не из пресс-релиза через этот скрипт — легко перепутать при проверке). Исправлено: схлопывать теперь только `[ ]{2,}` (пробелы), таб не трогать. Второй попутный баг: источники часто вставляют пустые `&nbsp;`-ячейки только для отступа — при разбивке по табам это давало кучу пустых колонок; теперь пустые (после очистки `\xa0`) ячейки построчно дропаются. Урок: при проверке «заработало ли» — проверять, что результат пришёл именно из ожидаемого источника/шага, а не просто что артефакт (таблица) где-то в файле присутствует.

## Формат «OME Report» — доработки после обратной связи (2026-08-25)

- **Транскрипт**: обрезка убирала мусор только В КОНЦЕ (после «This article was generated»), но не в НАЧАЛЕ — шапка сайта (меню, промо, виджет котировки) просачивалась в начало вкладки. Исправлено: ищем первый абзац длиннее ~120 символов (реальный лид статьи), всё до него — отрезаем. Заодно нашли, что реальный лид-абзац + «Key Takeaways» инвестинг.com — это ценная часть саммари источника, которую раньше срезали вместе с мусором (начинали с «Executive Commentary», а не с лида).
- **Пресс-релиз**: жирный текст (`<strong>`/`<b>` в исходном HTML) раньше терялся при конвертации в текст — теперь `html_to_text.py` сохраняет его как `**маркеры**`, а `build_report_html.py` рендерит их как `<strong>`.
- **Копирование таблиц**: кнопка «📋 Копировать в Excel» у каждой HTML-таблицы, копирует TSV (табами) через `document.execCommand('copy')` — совместимо с `file://`, в отличие от современного Clipboard API.
- **Комментарий — два раздела** внутри вкладки (переключатель-пилюля): «Публикация» (готовый текст в доме. стиле, см. `examples/report-style-templates.md`) и «Как собран» (рабочие заметки — расхождения, что не проверено). `build()` теперь принимает ОБА пути (`publication_path`, `commentary_path`) отдельно.

## Формат «OME Report» — второй раунд правок (2026-08-25)

- **Заголовки секций** (Key Takeaways, Company Performance, Financial Highlights, Risks and Challenges, Q&A и т.д.) теперь распознаются по известному списку (`KNOWN_HEADERS`) и рендерятся как `<h3>`, а не сливаются с обычным текстом.
- **Буллеты**: источник часто разделяет пункты списка ОДИНАРНЫМ переносом строки (не пустой строкой) — из-за этого весь список раньше слипался в один абзац/один `<li>`. Теперь после заголовка из `KNOWN_LIST_HEADERS` (Key Takeaways, Risks and Challenges, Financial Highlights) блок дробится построчно на реальные пункты `<li>`.
- **Таблицы**: добавлено объединение ячеек «$» + число в одну (было две колонки), подсветка строк «Total/Net loss/EBITDA» жирным, и вынос сплошного colspan-заголовка (короче остальных строк) в подпись-капшн над таблицей вместо кривой `<th>`-строки.
- **4-я вкладка «Презентация»** (опционально) — встраивает PDF инвесторской презентации КАК ЕСТЬ через `<iframe>` (плюс ссылка «открыть в новой вкладке») — не пересобирается в текст, показывается оригинал. Параметр `presentation_pdf` в `build()`, относительный путь от папки с итоговым HTML.

## Формат «OME Report» (с 2026-08-25)

По просьбе владельца — вместо (в дополнение к) разрозненных .md/.txt/.pdf файлов собирается единый HTML-файл на вкладках для удобного локального чтения: **Комментарий** (интерпретация) / **Пресс-релиз** / **Транскрипт**. Название формата — «**OME Report**», не публикуется никуда (не Artifact, не веб), только локальный файл, открывается двойным щелчком в браузере. Имя файла: `<Тикер> <квартал> - отчёт.html`, лежит в корне `X:\Research\VS\<Тикер> US\` рядом с `.md`-заметкой. Собирается скриптом `automation/build_report_html.py` (не писать HTML/конвертацию текста вручную заново). Акцентный цвет — `#1B2A6B` (тот же тёмно-синий, что уже используется в PPTX-материалах владельца — для визуальной согласованности). Первый пример — `X:\Research\VS\XE US\XE 2Q26 - отчёт.html`. Известное ограничение: если исходная HTML-таблица в релизе оформлена не через `<td>`, а неразрывными пробелами (`&nbsp;`) — такая таблица не конвертируется в HTML-таблицу и остаётся текстом; обычно это дублирующая "summary"-таблица, а не единственный источник цифр — не критично.

## Автоматизация и хранение прогресса (с 2026-08-25)

- Идеальный формат хранения по компании — растущий .md-файл, не разовый прогон (см. «Правила» выше). Реальное место — `X:\Research\VS\<Тикер> US\`, но диск не всегда подключён.
- Решение: локальный стейджинг + скрипт синхронизации на диск X при подключении, запускается через Планировщик задач Windows. Детали, скрипт и инструкция по настройке — `automation/README.md` и `automation/sync-to-diskX.ps1` в этом репозитории.
